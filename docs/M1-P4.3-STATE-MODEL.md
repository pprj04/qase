# M1-P4.3 — Canonical State Model (Phase 1)

Built strictly from the ACTUAL implementation — every transition below was
verified against server/missions.js, store.js, fixValidation.js,
findingIntelligence.js, validationLoop.js, index.js route handlers, and the
governor. Nothing invented.

## 1. Mission

- **Identity**: `id` (uuid), `projectId`, optional `workspaceId` /
  `createdByUserId` / `correlationId` / `idempotencyKey`.
- **Source of truth**: missions.js `store` Map → `.qase/missions.json`.
- **Owner/parent**: Project (soft ref `projectId`).
- **Immutable after create**: `id`, `createdAt`, `projectId`, `idempotencyKey`
  (creation-time integration fields — updateMission explicitly does not allow
  changing `workspaceId`/`correlationId`... it DOES list them as allowed. Only
  `id` and `createdAt` are truly immutable).
- **Mutable**: name, type, targetUrl, objectives, capabilities,
  successCriteria, constraints, status, sessionId, qualityScore, verdict,
  improvementPrompt, releaseReady, findings[], summary, completedAt,
  iterations[], currentIteration, context, stopReason, iterationMetadata[],
  startedAt, estimatedDuration, queuedAt, failureReason, cancelledAt,
  cancellationReason.
- **Terminal states**: `completed`, `failed`, `aborted`, `cancelled`, `timeout`
  (TERMINAL_STATUSES, missions.js:40).
- **Timestamps**: createdAt (create), queuedAt (governor submit), startedAt
  (slot grant), completedAt (finalize), updatedAt (every write).

### Mission status transition matrix (ACTUAL, as implemented today)

```
created → queued → running → { completed | failed | aborted | timeout }
created → queued → cancelled
running → interrupted (boot reaper only) → terminal via revalidate-restart
running → aborted (manual stop / honesty guard for dead sessions)
running → failed (runtime start errors, blocked target, LLM dead loop)
running → timeout (governor wall-clock sweep)
queued → failed (blocked target / device check while queued... verify: those
          checks run at start; queued missions fail via pump start failure → failed)
created → running (direct start without governor? — legacy /start route sets
          running directly at index.js:1858/2058/2173 when slot granted immediately)
```

**Invalid today-but-possible (to be closed in P2)**: any → any via PATCH
updateMission (no validation). Terminal → running resurrection. The P2
validator enforces the matrix above and makes illegal transitions a no-op
(persist + return unchanged, log warn) rather than an error for in-process
writers, while PATCH gets 409. (Final choice documented in §7.)

### Key transition call-sites (verified)
- queued: index.js:1793/1887/2077/2217 (governor submit paths), boot requeue.
- running: index.js:1858/2058/2173/2931 (slot granted, session created).
- failed: 1788/1878/1881/2068/2071/2207/2211/2911/2916/2947 (start errors,
  blocked target, createSession failure).
- aborted: 2007 (manual stop), sweep stuck-session.
- timeout: sweep wall-clock (missionGovernor.js).
- interrupted: boot reaper only (recoverInterruptedMissions, missions.js:431).
- completed: finalizeMission (:253) via finalizeMissionFromSession (index.js:2608)
  and capabilities.js:515.

## 2. Session

- **Identity**: `id` (uuid), title, `projectId`.
- **Source of truth**: store.js `sessions` Map → `.qase/sessions.json`.
- **Owner/parent**: Project; referenced by mission.sessionId (1 mission → N
  sessions over iterations; mission.sessionId = latest).
- **Statuses (actual)**: `running`, `idle` (normal agent end), `awaiting_input`,
  `error`, `interrupted` (watchdog/manual stop), `done` (agent.js:567 legacy
  done). Watchdog can set `interrupted` via detail message.
- **Terminal-ish**: idle/error/awaiting_input/done/interrupted. There is NO
  single terminal set; status can be set repeatedly. Sessions are NOT
  transition-validated — product semantics are append-only transcript + status.
  P2 does not add session transitions (out of scope, minimal change).
- **Timestamps**: createdAt, lastActivity (touched by messages/activity), no
  completedAt. Store prune by lastActivity newest-first.

## 3. Iteration

- **Identity**: sequential `number` within mission (`currentIteration + 1`);
  `sessionId` links to the session that produced it.
- **Storage**: embedded — `mission.iterations[]` (recordIteration) AND
  `mission.iterationMetadata[]` (validationLoop.js, loop-specific fields).
- **Immutable once recorded**: number, sessionId, ranAt.
- **status**: `completed` at record time (recordIteration hardcodes
  'completed'); iterationMetadata.status uses ITERATION_STATUS lifecycle
  (created/running/assessing/deciding/completed/revalidation_required/terminal).
- **Revalidation**: creates a NEW iteration (new session, new number) — never
  overwrites history (guard: same sessionId skip). history preserved.

## 4. Finding

- **Identity**: `id` (uuid), `projectId`, `sessionId`, `missionId` (soft refs).
- **Source of truth**: findings.js array → `.qase/findings.json`.
- **Three independent status fields** (documented, not unified):
  1. `status` — simple kanban: open / in_testing / resolved / closed
     (findings.js:30 VALID_STATUSES).
  2. `finding_status` — lifecycle: DETECTED→VERIFYING→VERIFIED→CLASSIFIED→
     TRIAGED→REPORTED (+ FALSE_POSITIVE/DUPLICATE/INCONCLUSIVE/
     UNREPRODUCIBLE/RESOLVED/REOPENED) — strictly validated by
     LIFECYCLE_TRANSITIONS (findingIntelligence.js:650) incl. VERIFIED
     evidence gate.
  3. `review_status` — unreviewed/… (setReviewStatus).
- **fixStatus** (revalidation verdict, per finding): fix_validated /
  still_broken / partial / regressed / unable_to_verify (fixStatusEngine,
  deterministic; stored on finding after validation run completes).
- **Relationships**: `evidence[]` inline refs; `evidenceRefs` = WorkflowStep IDs
  (NOT evidence-graph node IDs — P1 contract); evidence-graph edge
  SUPPORTS(finding, evidence) via linkEvidenceToFinding.
- **Delete**: deleteFinding leaves evidence edges + test-case links cleaned
  via removeTestCaseFromAllFindings? (verify: linkTestCase exists; delete path
  P6 check).

## 5. Evidence

- **Identity**: evidence-graph node `id`, `type` (30+ types: screenshot,
  console, network, workflow_step, dom_snapshot, reasoning, observation…).
- **Owner/parent**: `sessionId` (+ `missionId` when known at capture).
- **Source of evidenceGraph.js: createEvidence/collectSessionEvidence.**
- **Immutable content**, integrity hash (computeIntegrityHash), status derived
  (determineEvidenceStatus: VERIFIED/ACTIONABLE/WEAK/INSUFFICIENT from count +
  source diversity).
- **Relationships**: typed edges — SUPPORTS(evidence→finding),
  DERIVED_FROM(observation→evidence), RELATES (finding↔observation),
  PRECEDES(iteration→iteration), CORRELATES(evidence↔evidence),
  INFORMS(assessment→decision), DRIVES(decision→iteration).
- **Two classes of capture**: collectSessionEvidence (persisted graph) vs
  agent inline `session.findings[].evidence` (SSE-only, not persisted — known
  limitation, honest).

## 6. Validation (fix-validation run)

- **Identity**: run `id`, `findingId`, `idempotencyKey`, `trigger`
  (manual/auto/scheduled).
- **Statuses (VALIDATION_RUN_STATUSES)**: REQUESTED → RUNNING → COMPLETED /
  FAILED (+ cancelled? verify: reaper maps queued/running/requested→FAILED
  'interrupted_by_restart' at boot; QUEUED exists in reaper mapping).
- **Guards**: one active run per finding (409); boot reaper; idempotency key;
  fixStatus from deterministic engine only — never LLM.
- **Owner**: finding (soft ref); snapshot of finding at run start
  (snapshotFinding) so verdicts reference immutable state.

## 7. P2 implementation decision (centralized transition validation)

Smallest safe mechanism for a single-process JSON-store architecture:

1. New `server/stateTransitions.js` — single source of truth for the mission
   status matrix + `attemptMissionTransition(current, proposed, { actor,
   reason })` returning `{ ok, legal, status, reason }`. Legal matrix =
   the ACTUAL call-sites in §1; everything else illegal.
2. `updateMission(id, patch)`: if `patch.status` present and differs from
   current → run validator. Illegal → log warn `[state] illegal transition
   ignored` + drop ONLY the status field (other fields still applied), return
   mission unchanged w.r.t. status. This keeps all 20+ call-sites working for
   legal transitions and makes illegal ones no-ops instead of crashes —
   smallest safe change, no route changes needed.
3. `finalizeMission`: unchanged guard (terminal → return existing). Keeps
   idempotency.
4. PATCH /api/missions/:id (index.js:1618): validate status transitions —
   illegal → 409 `{ error, code: 'ILLEGAL_MISSION_TRANSITION', from, to }`.
   Legal non-status fields unchanged.
5. Governor pump/sweep/reaper paths use updateMission → automatically
   validated. Governor tests (17/17) must stay green.
6. Timestamps/reasons: transition validator stamps `statusChangedAt` is NOT
   added (new field churn); instead ensure failed/aborted/timeout always carry
   failureReason/stopReason/cancellationReason respectively where the writer
   already provides them (verified call-sites do).

Invalid transitions (closed by P2): terminal→any (resurrection), created→
completed/failed/aborted/timeout (skip queue/run), queued→completed (must run
first — except boot-reaper interrupted path), running→cancelled (product uses
aborted for running stop), created→timeout.

## 8. Edge cases verified

- Boot reaper: running→interrupted at boot only (recoverInterruptedMissions).
  P2 must allow interrupted→queued (requeue) and interrupted→terminal.
- Revalidate: revalidate route creates new session → new iteration →
  finalizeMission again (mission must be non-terminal? revalidate on terminal
  mission: index.js:2981 finalizeMission call after new session — check guard;
  verify in P2 tests: revalidate on completed mission is a legal product path
  (Phase 9.2: REVALIDATE decision → iteration N+1). So `completed → running`
  IS legal on revalidate (it re-opens the mission with a new session). This is
  the one sanctioned resurrection — handled as special case in the matrix.
- Lazy finalize on GET: finalizeMissionFromSession guards on terminal status.
- Governor sweep terminal-reconcile: memory QUEUED/RUNNING vs persisted
  terminal → release slot without writing status again (already terminal).
- `recordIteration` skip-guard by sessionId — revalidation records a distinct
  iteration (never corrupts history).


## 9. Conclusion

The model is sound; the gap is enforcement. P2 adds a single validator module
+ updateMission guard + PATCH 409. Everything else (governor, pipelines,
reaper, revalidate) flows through updateMission/finalizeMission and inherits
enforcement without modification.
