# M1-P4.4 Phase 1 — Persistence Contract

> This document states what the QASE persistence layer **actually guarantees** after M1-P4.4.
> Source: Phase 0 audit (docs/M1-P4.4-PERSISTENCE-AUDIT.md) + Phase 2–5 implementation.

## 1. Durable vs runtime-only data

**Durable (`.qase/*.json`, survives restart):**
sessions, missions, findings, evidence graph, fix-validations, replay runs,
ux-assessments, test-cases, workflows, knowledge, regression-runs, schedules,
baselines index, projects, config.

**Runtime-only (rebuilt or dropped on restart):** live browser handles, mission
governor slots/queue positions, SSE subscriber lists, in-flight LLM turns,
`liveSessions` weakmap, watchdog timers, running validation executors.

**Durable but ephemeral by design (see §7):** `.qase/artifacts/<runId>/` replay
artifact dirs, `.qase/artifacts/baselines/<id>/`.

## 2. Authoritative store per entity

| Entity | Authority | Copies elsewhere (non-authoritative) |
|---|---|---|
| Mission | missions.json | `mission.summary` inside session, UI list cache |
| Session | sessions.json | mission.sessionId pointer, evidence sessionId refs |
| Finding | findings.json | session-embedded copies (Phase 11 migration moved them out), evidence edges |
| Evidence node/observation/edge | evidence-graph.json | none |
| Fix validation run | fix-validations.json | finding.fixValidationRef pointer |
| Replay run | replay-runs.json | artifacts/<runId>/ dir |
| Test case / Workflow | test-cases.json / workflows.json | finding.testCaseIds back-refs |
| Schedule | schedules.json | scheduler in-memory ticks |
| Baseline | baselines.json + artifacts/baselines/ | replay baselines |

**One writer per file, always the module that owns the entity.** No duplicate
writers exist (verified Phase 0 §2).

## 3. Flush guarantees

| Store | Normal write path | Max data-loss window (before P4.4) | After P4.4 |
|---|---|---|---|
| sessions | 250 ms debounce | ≤500 ms on crash; **unbounded on SIGTERM** | **0 on graceful shutdown** |
| missions | 500 ms debounce | ≤500 ms on crash; unbounded on SIGTERM | **0 on graceful shutdown** |
| findings | 250 ms debounce | same | **0** |
| evidence-graph | 250 ms debounce | same | **0** |
| fix-validations | 250 ms debounce | same | **0** |
| replay-runs | 250 ms debounce | same | **0** |
| ux-assessments | 250 ms debounce | same | **0** |
| test-cases / workflows / schedules / knowledge / baselines | 250 ms debounce / immediate | same | **0** |
| regression-runs | 250 ms debounce | same | **0** |

**Crash (SIGKILL / container pause)**: last ≤250–500 ms of mutations may be
lost — accepted, atomic rename means the file is never corrupt, only stale.
**Graceful shutdown (SIGINT/SIGTERM)**: all pending debounced writes are
flushed synchronously before exit (Phase 2). Tests cover: single pending
store, multiple pending stores, repeated signal, no pending writes, flush
failure during shutdown.

## 4. Shutdown guarantees

1. First signal → flush all dirty stores (idempotent registry), then close
   browsers, then exit 0. Each store logs `flushed` / `flush-failed`.
2. Second signal → immediate exit 1 (do not hang on a wedged flush).
3. Flush is **synchronous** (atomicWrite) — bounded by disk speed, no
   promise-hang risk. Total shutdown budget ≈ seconds even at 31 MB stores.
4. A flush failure of one store never aborts the others; failures are logged
   with the store name.

## 5. Recovery behavior on restart

| Event | Behavior |
|---|---|
| Mission in running/awaiting_input w/o live session | → `interrupted` (recoverInterruptedMissions) |
| Mission persisted as `queued` | re-submitted to governor FIFO (M1-P4.2) |
| Fix validation in QUEUED/RUNNING/REQUESTED | → FAILED `interrupted_by_restart` |
| Session status running/awaiting_input | → `interrupted`, pendingQuestion cleared |
| Illegal mission status transition detected | dropped by stateTransitions guard (P4.3) |

## 6. Corruption behavior

**Uniform rule after Phase 5:** on JSON parse failure a store:
1. Renames the corrupt file to `<file>.corrupt-<epoch>` (preserved for
   forensics; never overwritten silently),
2. Logs a LOUD structured line `[store] CORRUPT ...`,
3. Starts from empty — except evidence-graph and fix-validations which
   already behaved this way and remain unchanged,
4. Boot continues (a single corrupt store never blocks the server).

Before P4.4: 8 of 17 stores silently started empty with no preserved file
(sessions, missions, findings, replay-runs, ux-assessments, test-cases,
workflows, knowledge, regression-runs, schedules, baselines, projects).

## 6a. What persistence failure means for each store (truth table)

| Store | If save fails mid-flight | If load finds corrupt JSON |
|---|---|---|
| sessions | stale file, load recovers from it | `.corrupt-<ts>` preserved, starts empty |
| missions | stale file; recovery marks lost-running as interrupted | `.corrupt-<ts>` preserved, starts empty |
| findings | stale file | `.corrupt-<ts>` preserved, starts empty |
| evidence-graph | stale file | `.corrupt` preserved (pre-existing), starts empty |
| fix-validations | stale file | `.corrupt` preserved (pre-existing) |
| all others | stale file | `.corrupt-<ts>` preserved, starts empty |

**A store is never replaced with empty content while the on-disk file is
valid** — atomicWrite guarantees the old content survives a failed write.

## 7. Retention rules (Phase 3)

| Store | Rule | Preserves |
|---|---|---|
| missions | cap count (default 400). Prune order: (a) terminal demo/test P42|p4|gate|smoke debris older 30d, (b) oldest terminal missions, (c) never non-terminal, never flagged, and always keep most recent 200 terminal | findings (they carry own copies), evidence (immutable nodes), reports |
| replay-runs | cap count (default 400), oldest-first, spare referenced artifacts | artifacts referenced by kept runs |
| ux-assessments | cap count (default 400), oldest-first | evidence edges to pruned assessments are informational |
| sessions | existing 12 MB / 50-count budget (P4.1) | findings stay (own store) |
| evidence-graph | capped at 60,000 evidence nodes (default): prunes oldest evidence with no links (zero-degree) first, then oldest unlinked observations, per-batch with total cap | findings' evidence chains: only zero-degree nodes are eligible; linked evidence is NEVER pruned |
| artifacts | orphan-only deletion (Phase 4): dirs not referenced by replay-runs, baselines, or evidence `artifactPath`/screenshot refs, older than 30 days | any referenced artifact |

All cleanup: dry-run report first (`GET /api/v1/diagnostics/store-hygiene` and
`GET /api/v1/diagnostics/artifacts/orphans`), deletion only via
`POST /api/v1/diagnostics/store-hygiene/cleanup` or
`POST /api/v1/diagnostics/artifacts/cleanup` with explicit `apply:true`,
auth-gated (requireApiToken), fully logged, deterministic, safe to repeat.

## 8. Artifact retention rules

- **Referenced artifacts are never eligible.** A referenced artifact is one whose
  `artifacts/<dir>` appears in: replay-runs.json (`artifactPath`, trace/video/screenshot
  paths), baselines.json (artifactPath), evidence-graph nodes (`artifactPath`,
  `screenshotPath`, `capturedStep.artifact`, video/trace fields), missions.json
  (artifactPath/screenshotPath), findings.json (evidenceRefs→capturedSteps artifacts,
  artifactPath), sessions.json (capturedSteps artifacts).
- Orphan = none of the above, older than `ARTIFACT_ORPHAN_DAYS` (default 30).
- Deletion is recursive `rm -rf` of the artifact dir, logged with reclaimed bytes.

## 8a. Blocking vs informational integrity failures

| Code | Class | Meaning |
|---|---|---|
| MISSION_SESSION_MISSING | INFO | session pruned by retention — expected |
| FINDING_SESSION_MISSING | INFO | session pruned — finding keeps its own copy |
| MISSION_COMPLETED_MISSING_SUMMARY | WARNING | finalize skipped summary — check finalizeMission callers |
| MISSION_BAD_STATUS | ERROR (blocking) | status not in MISSION_STATUS enum |
| MISSION_MISSING_ITERATIONS / SESSION_MISSION_LINK_MISSING etc. | ERROR (blocking) | referential break beyond known-benign set |
| ARTIFACT_DIR_CORRUPT | WARNING | kernel-corrupted dir — removable via cleanup (it is by definition unreferenced-enumerable) |
| orphan artifacts / stale replay runs | INFO | cleanup candidates |

## 9. Maximum reasonable store sizes (post-retention steady state)

| Store | Budget |
|---|---|
| evidence-graph.json | ≤ 60,000 evidence nodes (file ~45–60 MB serialize; 31 MB today / 40.7k nodes → not yet capped) |
| missions.json | ≤ 400 missions (~2 MB) |
| sessions.json | 12 MB serialized budget (existing) |
| replay-runs.json | ≤ 400 runs (~270 KB) |
| ux-assessments.json | ≤ 400 assessments (~1.2 MB) |
| findings.json | uncapped by design (findings are the product) — monitor via diagnostics |

## 10. References that may legitimately become stale (NOT failures)

- finding.sessionId / mission.sessionId → pruned session (INFO)
- evidence edges → pruned/absent finding (INFO, edges kept for graph integrity)
- findings.evidenceRefs → workflow step IDs that no longer exist in a pruned
  session's capturedSteps (INFO — fix-prompt falls back gracefully)
- mission.testCaseIds → deleted test case (existing cleanupTestCaseReferences handles)

## 11. Limitations (honest)

- Single-process JSON persistence; no fsync — a host-level crash in the ~ms
  rename window can theoretically lose the rename. Accepted at this scale.
- Crash (SIGKILL) still loses ≤ debounce-window mutations — by design; the
  atomic rename guarantees the previous good state.
- Evidence-graph prune only removes zero-degree nodes; linked chains from
  ancient missions keep the graph growing slowly. Next phase should introduce
  per-mission compaction.
- No write-failure metrics endpoint yet (P4.5 observability scope).
