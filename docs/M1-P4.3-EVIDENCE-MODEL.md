# M1-P4.3 — Evidence Model (Phase 4)

Documented from the ACTUAL implementation (server/evidenceGraph.js, 1,251
lines; 40,728 nodes live). Nothing invented — every type, edge, and field below
exists in code today.

## 1. Canonical relationship chain

```
Mission ──HAS_ITERATION──▶ Iteration ──HAS_SESSION──▶ Session
   │                            │                          │
   └── (missionId ref)          │                          PRODUCED
                                │                          ▼
                                │                       Evidence node
                                │                     (ev_xxxx, immutable,
                                │                      integrity hash)
                                │                          ▲
                                │              DERIVED_FROM│SUPPORTED_BY
                                │                          │
                                └── produced ──▶ Observation (obs_xxxx)
                                                       ▲
                                             RELATES/AFFECTS
                                                       │
                                                   Finding
```

- `mission.iterations[][].sessionId` → session; `session.id` → evidence nodes
  (`evidence.sessionId`); `SUPPORTS` edge: evidence → finding.
- Findings ALSO carry inline `evidence[]` refs + `evidenceRefs` (WorkflowStep
  IDs — NOT graph node ids; documented in M1-P1 contract; unchanged).

## 3. Node types & edge types (as implemented)

NODE_TYPES: mission, iteration, session, action, observation, evidence,
finding, assessment, decision.

EDGE_TYPES: has_iteration, has_session, produced, supported_by, supports,
affects, produced_decision, belongs_to, precedes, caused_by,
correlates_with, derived_from, linked_to.

## 4. Evidence node shape (createEvidence, evidenceGraph.js:230)

| field | provenance metadata |
|---|---|
| id | `ev_` + uuid12 (immutable) |
| missionId / iterationId / sessionId | owner chain (nullable at capture; session capture usually has sessionId, missionId filled when mission context known) |
| type | one of EVIDENCE_TYPES (default observation) |
| source | 'agent' \| 'browser' \| 'network' \| 'system' — WHAT PRODUCED IT |
| timestamp | when produced |
| target | URL / selector / element observed |
| action | browser action that produced it |
| observation | human-readable what was observed |
| payload | raw data (error text, response body, DOM snapshot) |
| confidence | 0–1 (computed via computeEvidenceConfidence; weights: source reliability .30, reproducibility .25, source count .20, consistency .15, completeness .10) |
| integrity | non-crypto hash — mutation detection (computeIntegrityHash / verifyIntegrity) |
| metadata | free-form extra |
| createdAt / createdBy | creation provenance |

Every evidence node answers: what produced it (source+createdBy), when
(timestamp/createdAt), which mission/session/iteration it belongs to
(missionId/iterationId/sessionId), which finding it supports (SUPPORTS edge),
its type, its location/reference (target/payload), and its verification
standing (EVIDENCE_STATUS verified/partially_verified/unverified via
determineEvidenceStatus).

## 5. Derived statuses (deterministic, not LLM)

- `determineEvidenceStatus` — verified requires count + source diversity
  thresholds (VERIFIED needs ≥2 evidence from ≥2 sources; mirrors Phase 18
  finding gates).
- `computeEvidenceCoverage` — % of findings with sufficient evidence.
- `detectOrphans` (graph-internal) — evidence without session/mission,
  observations without evidence, broken edges. M1-P4.3's stateIntegrity.js
  adds the cross-store checks (findings→missions, missions→sessions, duplicate
  ids, impossible timestamps).
- Historical evidence is IMMUTABLE (getHistoricalEvidence reads only);
  compareIterationEvidence diffs iterations without mutating them.

## 6. Capture paths (what actually writes evidence)

1. `collectSessionEvidence` — post-turn hook captures workflow steps,
   screenshots, console/network from the live browser into the graph
   (persisted).
2. `createObservation` + `linkObservationToEvidence` — reasoning observations
   derived from evidence (DERIVED_FROM edges).
3. Agent inline `session.findings[].evidence` — SSE-only, NOT persisted to the
   graph (known honest limitation; unchanged in this phase).
4. `validationExecutorCore` — fix-validation attempts write step_outcome /
   assertion evidence under the validation run's session (Phase 18 chain).

## 7. Integrity & duplication

- Duplicate suppression: evidence ids are content-addressed at creation only by
  uuid — the jaccard-dedup applies to FINDINGS, not evidence. Duplicate
  evidence within a session is prevented by capture-path design (one node per
  step/console event; collectSessionEvidence skips steps already captured —
  verified in P1 audit `capturedSteps`).
- No evidence is deleted on finding delete (edges remain) — stateIntegrity
  detects orphaned SUPPORTS edges as info-level (graph-internal detectOrphans
  reports them as warnings).

## 8. What M1-P4.3 changed (nothing in the graph itself)

Nothing. This phase only DOCUMENTS the model and adds cross-store integrity
checks (stateIntegrity.js) + the diagnostic endpoint. Graph growth (40k nodes /
28MB file) remains the M1-P4.4 store-scaling problem.
