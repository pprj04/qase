# M1-P4.2 — Concurrency & Execution-Queue Audit (Phase 0, inspect-only)

Scope: agent-mission execution (POST /api/v1/missions → agent/LLM/Chromium →
finalize). Replay suites, UX sweeps and fix-validation runs are adjacent
subsystems documented for resource interaction only.

## 1. Current architecture (verified, file:line)

- **No queue. No mission concurrency limit.** Greps for
  `concurrent|slot|queue|semaphore|inFlight` in `server/` hit only config
  knobs, the replay worker pool, and the pipeline idempotency flag.
- `concurrentRuns` (default **3**, `QASE_PARALLEL`, server/config.js:76,102)
  bounds **replay test suites only** (index.js:1095, scheduler.js:226,
  replay.js:1096). Agent missions read no concurrency knob → unbounded.
- Every mission start funnels through `createSession()` → `ensureRuntime()`
  → `startTurn()` → detached `runTurn` (fire-and-forget, index.js:287-293).
  One Chromium per session (browserBridge), N concurrent missions = N
  Chromiums + N parallel LLM conversations.

## 2. Status model (missions.js)

- Declared (missions.js:30-32): `created, queued, running, completed, failed,
  aborted, cancelled, timeout` (+ reaper-only `interrupted`).
- **`queued`, `cancelled`, `timeout` are never written by any code path.**
- Terminal set (missions.js:38): completed/failed/aborted/cancelled/timeout
  (`interrupted` is restartable by design).
- `startedAt`: declared + allowlisted but **no writer today** (66/2544 live
  records carry it, from an older path). `failureReason` is passed to
  `finalizeMission` (index.js:2534) and **silently dropped** (missions.js:260-267).
- Live distribution: created 2129, completed 182, aborted 124, interrupted 76,
  failed 27, running 6 — all six stuck ones have `startedAt:null`, no stop
  reason (consistent with the stuck paths below).

## 4. Stuck-mission paths (the bug class this build must close)

1. Session ends **`idle`** (turn-timeout abort, model-silent, or runTurn end
   without report) → `idle` ∉ lazy-finalize's done/error/interrupted set →
   mission stays `running` forever (M1-P4.1 Run-3 reproduced this: 0-message
   session idle at 20 min, mission `running` 75+ min).
2. Session `done` but **nobody polls** GET /missions/:id → lazy finalize
   never runs (reaper skips it: session still exists) → polls-forever zombie
   (documented missions.js:410-417).
3. `awaiting_input` forever (interactive question never answered) → not in
   any complete set → mission `running` indefinitely.
4. **10 simultaneous missions** → 10 Chromiums + 10 LLM conversations on a
   ~6GB container → provider starvation (observed: empty responses, aborts).

## 5. Resource-leak paths

- `runResourceCleanup` browser-close branch is **dead code** — checks
  `record?.browser` which is never assigned (live records carry
  `bridge`/`runtime`); only session pruning actually frees browsers
  (index.js:158-161).
- Turn-timeout/idle aborts leave sessions `idle` → no finalize → browser held
  until a later `runTurn`'s `closeOtherBrowsers` or the (dead) cleanup branch.
- `record.dispose()` (runtime) only on `done` (agent.js:572) / config
  teardown / session delete.

## 6. Cancellation today

- POST /api/v1/missions/:id/stop (index.js:1928-1946): 409 unless
  `running`; aborts controller + `closeBrowser` + status `aborted`
  (`stopReason:'manual_stop'`). This is QASE's existing, tested cancellation
  architecture — reuse it.
- POST /api/sessions/:id/stop aborts a session but leaves any linked mission
  `running` (lazy finalize rescues only if polled).

## 7. Restart semantics today

loadSessions marks running/awaiting sessions `interrupted` → reaper marks
missions `interrupted` **only if the session record is gone**; otherwise the
mission stays `running` for lazy finalize (→ zombie paths above). Missions
`created`-never-started wait for explicit /start (no auto-resume — correct).
`queued` cannot exist today (never written).

## 8. Recommended minimal design (what M1-P4.2 implements)

**In-process execution governor** (no new service) — `server/missionGovernor.js`:

- Slots: `maxConcurrentMissions` (config.js: env `QASE_MAX_MISSIONS`, default
  **3** — parity with the replay pool default; clamped 1-10; settable via
  existing PUT /api/config, visible in GET /api/config). One slot = one agent
  execution (one session + Chromium + LLM conversation).
- `submit(missionId, {onStart})`: idempotent per mission; writes `queued`
  (+`queuedAt`) when no slot free; on grant: `running` + `startedAt` +
  onStart(). FIFO array, stable mission IDs, no duplicate entries.
- Release hooks: subscribe to `missionBus` terminal writes
  (`mission:finalized`/`mission:updated`) → `release()` → `pump()` starts the
  next queued mission. Completed/failed/aborted/cancelled/timeout/interrupted
  all release. Pump is synchronous, single-grant-per-slot.
- Governor watchdog (60s): (a) mission terminal but slot held → release
  (idempotent backstop); (b) running mission whose session settled
  (`idle|done|error|interrupted`, runtime not running) for >90s grace →
  invoke the existing honesty finalizer (`finalizeMissionFromSession`) →
  terminal → release — **closes stuck paths 1-3 without duplicating logic**;
  (c) hard wall-clock `missionTimeoutMinutes` (env `QASE_MISSION_TIMEOUT_MIN`,
  default 60, per execution/iteration) → abort + `failed`
  (`failureReason:'execution_timeout'`).
- Cancellation: `/stop` extended — `queued` → dequeue + `cancelled`
  (+`cancelledAt`, `cancellationReason`), never executes; `running` → existing
  abort path (status `aborted` stays — it is QASE's tested cancellation
  state; `cancelled` is introduced for queue-only cancels. No second
  architecture).
- Restart: after the existing reaper, missions persisted as `queued` are
  re-submitted (their spec lives on the mission record; a queued mission
  never had a worker, so requeue is safe and honest). No false resume of
  running executions (unchanged reaper semantics).
- API: mission objects gain `queuedAt`, `queuePosition` (computed while
  queued), `startedAt` (now actually written), `failureReason` (now
  persisted), `cancelledAt`, `cancellationReason`, `executionDurationMs`
  (computed). List responses add `queueDepth`. No new secrets.
