## 6. Known limitations (honest)

1. phase17-api flake under load (§4) — pre-existing, monitored.
2. Kernel-corrupted artifact dirs (15) cannot be enumerated or deleted from
   inside the container; reported as `unreadable[]`; host-level fsck is the
   only remedy. NOT VERIFIED whether they hold referenced data.
3. Artifact mtime reset on container restart → age gate defaults to 0;
   reference-hood is the only liveness signal (documented in the report's
   `note`).
4. Evidence-graph prune only removes zero-degree nodes; linked chains grow
   monotonically (41,664 nodes / 31 MB today — under the 60k cap).
5. Crash (SIGKILL) still loses ≤ debounce-window mutations by design;
   graceful shutdown is now lossless.
6. No fsync before rename — a host-level crash in the rename window could
   theoretically lose the rename. Accepted at this scale.
7. hygiene/artifact endpoints are single-process; concurrent cleanup +
   ingestion is serialized by Node's single thread (no torn files).

## 7. Remaining production risks

- missions.json still 13 MB with 2,627 records (1,710 stale shells are now
  RECLAIMABLE via the cleanup endpoint — ~1.1 MB; the rest are real history
  under the 400-cap policy once applied).
- findings.json uncapped by design (product data) — 8.9 MB today.
- Single-node JSON stores: no multi-writer, no compaction — fine for
  single-tenant QASE; revisit at M1-P5 (data layer) for multi-tenant.

## 8. Recommended M1-P4.5

**Operator observability + scheduling hardening**:
1. wire store flush failures + corrupt-preservations + hygiene summaries
   into a `/api/v1/diagnostics/persistence-health` aggregate (ops single
   pane);
2. optional scheduled hygiene (cron-like, still explicit-apply per run);
3. write-failure counters per store (P4.3 observability doc §6 gap);
4. phase17-api flake root-cause (likely needs per-request socket tuning);
5. THEN the operator may run the real cleanup (1,710 shells + 2,855 orphan
   dirs ≈ 173 MB) — intentionally left un-applied for a human decision.
