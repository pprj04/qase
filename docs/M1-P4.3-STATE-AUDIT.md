# M1-P4.3 — State & Persistence Audit (Phase 0, read-only)

Build: M1-P4.3 · Date: 2026-08-24 · Scope: mission/session/iteration/finding/evidence/
test-case/workflow/validation state — all writers, readers, persistence, races.

Method: direct code read of server/*.js + route inventory in index.js. No production
code was modified during this audit.

## 1. Sources of truth

| Entity | Source of truth | Persistence | Write pattern |
|---|---|---|---|
| Mission | `server/missions.js` `store` Map | `.qase/missions.json` (in-memory array → atomicWrite, 500ms debounce) | debounced, one writer module |
| Session | `server/store.js` `sessions` Map | `.qase/sessions.json` (atomicWrite, ~2s debounce via persistSoon; 15MB byte-budget prune) | debounced, single module |
| Finding | `server/findings.js` array | `.qase/findings.json` (atomicWrite debounced) | debounced, single module |
| Evidence | `server/evidenceGraph.js` node Map + edges Map | `.qase/evidence-graph.json` (28MB, tmp+rename via scheduleSave) | debounced, single module |
| Validation | `server/fixValidation.js` runs Map | `.qase/fix-validations.json` | debounced |
| Test case | `server/testCases.js` | `.qase/test-cases.json` | debounced |
| Workflow | `server/workflows.js` | `.qase/workflows.json` | debounced~? (verify) |
| Iteration | **embedded** in mission record (`mission.iterations[]`) | via missions.json | inherited |
| Schedule | `server/schedules.js` | `.qase/schedules.json` | debounced |

All stores load ONCE at module load and mutate in-memory Maps/arrays; a single
debounced atomicWrite per store mirrors to JSON. Node is effectively
single-threaded, so intra-process races are interleaving/atomicity-of-compound-
operation issues, not shared-memory torn writes. Real risks: (a) crash losing up
to debounce-window writes, (b) compound read-modify-write across `await` points,
(c) multiple modules writing the SAME field of the same entity.

## 2. Multi-writer inventory (mission status field)

`updateMission()` (missions.js:202) allows 20+ call-sites in index.js to set
`status` with **no transition validation** — including over a terminal status
(resurrection). `finalizeMission()` (:253) has a terminal guard but only for its
own call path. Direct writers to mission.status:

- index.js:1653 (create→? ), 1753, 1788, 1793, 1858, 1878, 1881, 1887, 1918,
  1986, 2007 (manual stop→aborted), 2058, 2068, 2071, 20xx, 2173, 2207, 2211,
  2217, 2691, 2911, 2916,  await transitions 2931, 2947.
- capabilities.js:515 — pipeline finalize
- index.js:2608+ `finalizeMissionFromSession` (session-driven finalize with
  idempotency guard + honesty guard) and :2981 (revalidate path).
- missionGovernor sweep() — terminal-reconcile (QUEUED/RUNNING memory vs
  persisted status), wall-clock timeout (→timeout), stuck-session (→aborted?).
- store.js runWatchdog() — session watchdog (20-min turn) can end sessions
  behind a mission.
- boot: recoverInterruptedMissions (running→interrupted).

Compound async writer chains: startMissionExecution (start route handler →
governor submitMission → queued → pump → start() → createSession → setStatus
running), stop route (manual stop → releaseMission + updateMission aborted),
reaper (boot: recoverInterruptedMissions), sweep (30s watchdog), lazy finalize
on GET detail (finalizeMissionFromSession called from GET /api/v1/missions/:id
when session done but mission still running).

## 3. Key risk findings

### R1 — updateMission permits illegal status transitions (HIGH)
No validation: `created → completed`, `completed → running` (resurrection),
`aborted → completed` etc. all pass. Terminal-status protection exists only
inside finalizeMission. Consequence: racing stop vs finalize can overwrite
completed→aborted or vice versa (last-writer-wins). No audit trail of who set a
status or when.

### R2 — Multiple independent finalizers, partially guarded (HIGH)
finalizeMissionFromSession (index.js:2608) guards on terminal check, but the
manual-stop handler (index.js:2007) and governor sweep can both fire after a
mission already completed, and updateMission doesn't re-check, so a completed
mission CAN be flipped to aborted (observed in P4.2 verify3: mission aborted at
886s after the turn watchdog ended the session — legal, but if finalize had won
the race the stop could overwrite it).

### R2b — Lazy finalize on GET has a TOCTOU window (MEDIUM)
GET /api/v1/missions/:id sees session done + mission running → calls
finalizeMissionFromSession → multiple awaits (quality scoring, webhooks) — a
concurrent stop/timeout finalizer can interleave. Both paths converge on
finalizeMission's terminal guard, so the outcome is bounded to whichever wins,
but failureReason/stopReason fields can end up written by the loser (fields
updateMission still writes on a terminal mission).

### R2c — updateMission allowed-fields list includes result fields (MEDIUM)
`status`, `failureReason`, `stopReason`, `completedAt` are settable by any of
the 20+ call-sites — including PATCH /api/missions/:id (index.js:1618 — patched
body directly into updateMission, gated by requireApiToken since M1-P3). An API
client can legally set status: 'completed' on a running mission via PATCH. This
is an API-level state integrity hole (still token-gated).

### R2c-observed — PATCH route mutates all allowed fields (verified live in P4.2)
The PATCH /api/missions/:id route at index.js:1618 passes request.body straight
into updateMission — a client can flip any allowed field including status.
Token-gated, but outside the transition contract.


### R3 — Iteration recording: last-iteration-wins on mission.findings (MEDIUM)
recordIteration (missions.js:327) sets `mission.findings = iteration.findings`
and `mission.currentIteration` monotonically. Multi-iteration missions: top-level
findings only reflect the LATEST iteration. Missions with
`findingsCount` from list endpoint compute counts from this list — so counts for
older iterations live only inside `iterations[]`, not on the summary. Acceptable
product semantics but a consistency trap for reports/UI (documented, not changed).

### R3b — recordIteration sessionId guard is string-equality only (LOW)
Same session re-finalized via a different path (e.g. lazy GET finalize racing
pipeline finalize) is guarded by `mission.iterations.some(it => it.sessionId ===
... )` — good. But iteration numbers are assigned as `currentIteration + 1`; two
concurrent recordIteration calls with different sessions could interleave push +
counter increment — practically impossible in-process (synchronous function), so
LOW.

### R4 — Session store byte-budget prune can delete active-session records (MEDIUM)
pruneOldSessions keeps newest by lastActivity with MIN_KEEP 5 / count cap 50 /
~12MB budget, spares running sessions — BUT it trims arrays on disk while
governor queue may reference queued missions whose sessions aren't created yet
(they're created on grant). No orphan risk to governor. Real risk: pruning a
session whose mission is still `running` in missions.json → GET mission detail
lazy-finalizes against a missing session? Verify: finalizeMissionFromSession
checks session existence? (index.js:2608 — it receives mission+session objects,
called from routes that already resolved the session). Missing-session fallback
exists at index.js:2627 for error/interrupted sessions. LOW–MEDIUM, verify in P6
integrity checks.

### R4b — Sessions prune keeps "running" sessions that are zombies (LOW)
spares status running — but zombie running sessions (server down) were reaped by
recoverInterruptedMissions at boot. Boot-time reaper marks missions interrupted;
sessions left 'running' on disk become orphaned running-session records — picked
up by P6 orphan detection.

### R4c — missions.json unbounded growth (MEDIUM)
No prune on missions.json — 2,310+ missions, 10.3MB pre-audit; grows with every
mission ever. Restart load parses the whole file; memory holds all missions. Not
P0 but the same class as the sessions 15MB issue that broke RL-1 twice. Same
byte-budget treatment as sessions is the M1-P4.4 candidate.

### R4d — evidence-graph.json 28MB non-atomic write path REMAINS (MEDIUM)
M1-P3 P0-1 fixed scheduleSave → tmp+renameSync, but loadFromDisk on parse
failure now logs LOUD and continues EMPTY — the 28MB file keeps growing; boot
parse ~319ms (performance suite); load-once pattern means a corrupted parse →
empty graph silently until ops notice. Integrity check (P6) should verify parse
health + orphans. NOT fixed here (scope: state consistency, not store growth).

### R5 — Event-bus name mismatch (already known, still true) (MEDIUM)
missions.js emits `mission:finalized`; listener registered as `finalized` —
webhooks dead. See M1-P3 risk register. Out of scope to fix here (would change
public event names) — document in P7 contract.

### R5b — mission:updated / mission:finding events unbounded listener growth (LOW)
bus.setMaxListeners(0) — intentional; fine.

### R6 — findings link integrity (MEDIUM)
`finding.evidence` is inline array of refs; `finding.evidenceRefs` are
WorkflowStep IDs, NOT evidence-graph node IDs (verified P1). syncSessionFinding
(agent flow) updates-or-inserts by finding.id — safe upsert. addFinding
duplicates guarded by jaccard dedup in intelligence layer, not at insert time.
Orphan risk: deleteFinding does NOT clean evidence-graph links (linkEvidenceToFinding
edges stay) — P6 detects; P4 evidence model documents edge types.

### R7 — Duplicate finalization of session→findings (LOW, guarded)
syncSessionFinding keyed on finding.id: agent creating finding twice with same
id → update not duplicate. addFinding with no id generates new — agent uses
stable ids? Agent finding ids are session-scoped uuids — safe.

### R7b — attachFinding vs syncSessionFinding duplication (LOW)
attachFinding pushes session.findings array into mission.findings (additive,
no dedup) — but finalize path overwrites mission.findings entirely via
finalizeMission(results.findings), making attachFinding during run redundant but
harmless (overwritten at finalize). Pre-finalize mission detail shows findings
only via attachFinding; post-finalize via results.findings. Two different shapes
same field — P7 documents.

### R7c — agent findings inline `evidence` (screenshots) are SSE-only (known)
Ephemeral screenshots in session.findings[].evidence — not persisted to
evidence-graph (only collectSessionEvidence captures steps). Known limitation,
documented in M1-P1/P4.2.

### R8 — Governor ↔ missions.json drift (MEDIUM)
Governor is memory-only queue state; persisted missions have `status: queued`.
Boot requeue (M1-P4.2 Phase 6) requeues persisted queued missions. Slots/queue
positions NOT persisted — restart while 3 running + 2 queued → 5 requeued? No —
boot requeues ALL non-terminal as queued (recoverInterruptedMissions reaps
running→interrupted; then queued ones re-submit). Drift risk: memory queued vs
persisted status mismatch after restart (mission says queued in memory-governor
but missions.json still says running until reaper rewrite) — reconciled by
reaper. Verified in P4.2 Phase 6 tests.

### R8b — governor releaseMission does not verify the mission record matches (LOW)
releaseMission just frees the slot; mission-record finalization handled by
callers. If a start() crashes before finalize, sweep terminal-reconcile catches
it within 30s. Bounded inconsistency window.

### R9 — fixValidation runs Map keyed by id (LOW)
transitionRun validates? (fixValidation.js:196) — verify in P1 model; boot
reaper exists (M1-P3 P0-2). Fix-validation lifecycle guarded by 409 on active
run for a finding (one active validation per finding) — enforced via
findByIdempotencyKey + status gates. Good pattern.

### R10 — Lagging deletion paths (MEDIUM)
deleteMission (missions.js:279) deletes the mission record only — iterations,
findings (with missionId), evidence (missionId nodes), sessions (mission-linked
via sessionId) all orphan. deleteSession (store.js:178) deletes session record
only — findings (sessionId), evidence (sessionId nodes), observations orphan.
deleteFinding leaves evidence edges. P6 detection + P3 fix (guard or cascade
notes) in scope.

### R10b — No FK enforcement anywhere (structural, by design of JSON stores)
All relationships are soft references by id. Integrity must be checked
explicitly (P6).

### R11 — Pagination state (production-critical endpoints)
| Endpoint | Current | Risk |
|---|---|---|
| GET /api/missions | full array (2,310 missions) | **unbounded** |
| GET /api/findings | full array (2,541+ findings, 6.3MB) | **unbounded** |
| GET /api/v1/missions | absent — uses /api/missions | gap |
| GET /api/test-cases | full array (425) | moderate |
| GET /api/workflows | full array (205) | moderate |
| GET /v1/evidence/stats etc. | already paginated | ok |
| GET /api/v1/missions/:id/evidence | paginated limit/offset + total | ok |
| GET /api/sessions | limited? | verify |

### R12 — Iteration embedded array can grow (LOW)
maxIterations default 3, cap-able via constraints — fine.

### R3-appendix — PATCH body whitelist audit
index.js:1618: `updateMission(request.params.id, request.body ?? {})` — the
`allowed` list in updateMission acts as the whitelist; status is in it. Phase 5
fields (stopReason, iterationMetadata) too. No additional hardening in P4.3
(that's M1-P4.4 API hardening), but transition validation (P2) will apply to
updateMission so illegal transitions are rejected server-side, closing R1/R2c
at the store layer for ALL writers including PATCH.

## 4. Priorities for implementation phases

- **P2 (transitions)**: guard updateMission + finalizeMission behind a single
  transition validation (`transitionMissionStatus`) — legal matrix from actual
  code paths, rejects terminal resurrection, preserves reasons, idempotent
  re-finalize. Applies to ALL writers (routes, governor, reaper, pipelines).
  PATCH keeps working for legal fields (non-status) — PATCH status via illegal
  transition now 409s.
- **P3 (consistency)**: integrity utility `server/stateIntegrity.js` with
  checkStateIntegrity({deep}) returning structured findings; used by P6
  diagnostic endpoint. Fix recordIteration semantics? NO — document (R3 is
  product semantics). Guard deleteMission/deleteSession against orphaning by
  counting refs + marking `orphanedAt` instead of silent cascade (smallest safe).
- **P4 (evidence)**: evidence-model doc from actual edge types + node kinds.
- **P5 (pagination)**: missions + findings + test-cases + workflows lists get
  optional limit/offset/total WITHOUT breaking existing full-array responses
  (limit omitted → full array, as today; limit present → {items,total,limit,offset}).
  Backward-compatible envelope for existing UI (public/app.js expects arrays —
  verify before shipping; if UI expects array, keep array shape when no limit
  param, envelope only when asked).
- **P6 (diagnostics)**: GET /api/v1/diagnostics/state-integrity (token-gated,
  structured output, severity, remediation).
- **P8 (concurrency)**: test file m1-p4.3-state.test.js with concurrent stop vs
  finalize, queue drain, restart consistency, revalidation history.
- **R4c/R4d (store growth) → recommended for M1-P4.4** (byte-budget for
  missions.json + evidence-graph split/archive).

## 5. Restart/recovery implications

Boot order (server/index.js): loadSessions → boot prune → loadMissions →
recoverInterruptedMissions (running→interrupted/aborted) → requeue queued →
governor resubmit → watchdogs start. Data-loss window = debounce (500ms–2s) per
store. SIGINT/SIGTERM flush not yet implemented (M1-P3 P1 deferred) — crash
loses ≤2s of writes. missions.json parse failure → EMPTY map (same as sessions)
with console.error only — a 10MB corrupted file = total mission-history loss.
(Recommendation for P4.4: keep backup rotation before overwrite.)

## 5b. Governor & state interplay (M1-P4.2 preserved)

Governor interacts with mission state through three channels: submitMission
(persisted queued), pump promotion (start() → updateMission running +
sessionId), sweep reconcile (terminal memory vs disk; timeout → mission
timeout). P2 transition validation must not break pump/sweep semantics —
verify against governor tests (17/17) after implementation.

## pump() start() wiring (M1-P4.2, per-mission starts Map)

Per-mission starts Map (fixed in P4.2 Phase 9): each queued entry carries its
own start function; pump invokes the right mission's start on promotion.
submitMission requires a start function. releaseMission cleans up starts Map.

## 6. Conclusion

State layer is single-writer-per-entity at the module level, but mission.status
has 20+ unvalidated writers and PATCH can flip any allowed field including
status. The single highest-value P4.3 fix: centralize status transitions behind
one validator that all writers go through, without changing external API shapes.
Pagination, integrity diagnostics, and evidence-model documentation complete the
phase. Store-growth management (missions.json, evidence-graph.json) is deferred
to M1-P4.4.
