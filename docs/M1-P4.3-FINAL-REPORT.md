Build: M1-P4.3 (mission/session/iteration/finding/evidence state consistency,

Date: 2026-08-24 · Status: **PASS** (aggregate gate: 0 blocking failures; see §10)

## 1. Executive summary

M1-P4.3 hardened the STATE layer without redesigning anything: mission status
transitions are now centrally validated for every writer (20+ call-sites,
governor pump/sweep, boot reaper, pipelines, and the public PUT route), the
five large collection APIs gained backward-compatible pagination, and a
read-only cross-store integrity diagnostic now reports orphan/consistency
issues with severity + remediation. All M1-P4.2 governor behavior is preserved
(17/17 governor tests green). Controlled E2E against new.drytis.com completed
with a fully consistent persisted state chain (mission → 1 iteration → session
→ 17 evidence nodes, 0 integrity errors).

## 2. Before / after architecture

**Before**: `updateMission()` accepted any status from any writer with no
transition validation — a racing writer or an API client could resurrect a
terminal mission (completed→running observed live during the P4.3 audit probe)
or fabricate completion. List APIs returned entire stores (missions 10.4MB,
findings 7.8MB per response). No cross-store integrity checks existed.

**After**: one validator module (server/stateTransitions.js) is the single
source of truth for the legal transition matrix; missions.js applies it inside
updateMission (drop-only-status on illegal, other fields still apply) and
finalizeMission (illegal finalize target → no-op, sweep reconciles). The PUT
route rejects illegal transitions with 409 ILLEGAL_MISSION_TRANSITION —
including the completed→running resurrection, which is reserved to the
revalidate route (it creates a new session/iteration; PUT would re-open a
mission around a stale sessionId). Pagination is opt-in via ?limit (no limit →
byte-identical full-array responses). stateIntegrity.js + GET
/api/v1/diagnostics/state-integrity (token-gated) report cross-store orphans.

## 3. State model (docs/M1-P4.3-STATE-MODEL.md)

Documented for Mission, Session, Iteration, Finding, Evidence, Validation:
identity, lifecycle, owner, mutable/immutable fields, terminal states,
timestamps, relationships, allowed transitions — every transition verified
against actual call-sites. Mission matrix: created→[queued|running|failed|
cancelled|interrupted], queued→[running|cancelled|failed|interrupted],
running→[completed|failed|aborted|timeout|interrupted], completed→running
(revalidate ONLY), interrupted→[queued|completed|failed|aborted], all
terminals→∅. Finding lifecycle (pre-existing, untouched): DETECTED→VERIFYING→
VERIFIED-gated chain from findingIntelligence.js. Fix-validation runs:
REQUESTED→RUNNING→COMPLETED/FAILED with boot reaper.

## 4. Transition model (implementation)

- server/stateTransitions.js — LEGAL_TRANSITIONS + isLegalMissionTransition +
  attemptMissionTransition (logs `[state] illegal mission transition ignored`
  and keeps current status; never throws).
- missions.js updateMission: status write reverted if illegal (field-scoped).
- missions.js finalizeMission: routes through validator; illegal target →
  returns mission untouched.
- index.js PUT /api/missions/:id: pre-check → 409 with from/to; blocks
  completed→running except via POST /revalidate.
- Sessions intentionally NOT transition-gated (append-only transcript
  semantics; smallest-change decision documented in STATE-MODEL §7).

## 5. Evidence model (docs/M1-P4.3-EVIDENCE-MODEL.md)

## 6. Pagination changes (server/pagination.js)

Backward-compatible contract: no ?limit → EXACT previous response (full array).
?limit=N → {items,total,limit,offset,hasMore}, stable caller-side ordering,
limit clamped to 500, invalid limit → 10, offset supported. Applied to:
GET /api/missions, /api/findings, /api/sessions (now also deterministically
newest-first), /api/test-cases, /api/workflows. Verified live: missions
no-limit 200 10.4MB (unchanged), ?limit=2 → envelope with total 2584; findings
limit=1 → total 3569; clamps verified (9999→500, abc→10).

## 7. Integrity checks (server/stateIntegrity.js)

Cross-store, read-only, never deletes. Codes: MISSION_SESSION_MISSING (info —
expected after session pruning), FINDING_SESSION_MISSING (info),
FINDING_MISSION_MISSING (warning), MISSION_ITERATION_COUNT_DRIFT (warning),
MISSION_DUPLICATE_ITERATION_SESSION (error), FINDING_DUPLICATE_ID (error),
MISSION_IMPOSSIBLE_TIMESTAMPS (error), MISSION_CREATED_WITH_COMPLETION
(warning), MISSION_COMPLETED_NO_ITERATIONS (warning), EVIDENCE_GRAPH_HUGE
(warning >60k nodes). Live result: 2,574 missions / 3,529 findings / 40,728
evidence nodes → **0 errors, 0 warnings, 3,665 info** (all pruning-expected).

Verified through live probes + tests: concurrent legal+illegal PUTs leave the
mission in a legal state (final ∈ {created, cancelled} for a non-started

before any PUT lands, and running→completed via PUT is legal (finalize surface)
— the concurrency-probe test uses autoStart:false to test terminal fabrication
specifically. Governor interactions (pump promotion, sweep reconcile, boot
requeue) flow through updateMission and inherit validation — mission-governor

## 13. Known limitations (honest)

1. Store-level validation is field-scoped, not transactional: an illegal
   status is dropped but other fields in the same PATCH still apply (design
   choice — smallest safe change; documented).
2. missions.json (10.4MB) and evidence-graph.json (28MB+) growth is NOT
   addressed (byte-budget/archive is M1-P4.4).
3. Sessions remain unvalidated transitions (product semantics).
4. PUT running→completed remains legal (finalize surface); guard relies on
   token auth.
5. Integrity check is point-in-time, not continuous; huge graphs (>60k) only
   warned.
6. Three finding status fields remain (unification is API hardening scope).

## 14. Remaining production risks

R4c missions.json unbounded growth · R4d evidence-graph 28MB non-atomic parse
ceiling · R5 event-bus name mismatch (webhooks dead) · PATCH field allowlist
breadth (non-status fields) · no rate limiting · single-tenant. All mapped to
M1-P4.4/P4.5 in the roadmap.

## 15. Recommended M1-P4.4 work

1. Store hygiene: missions.json byte-budget prune/archive (mirror sessions
   pattern) + evidence-graph split/archive.
2. API hardening: field-level PUT allowlist, unified finding-status contract,
   rate limiting.
3. SIGINT/SIGTERM flush of debounced persist timers.
4. Event-bus name fix (mission:finalized) behind a feature flag.
