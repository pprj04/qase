# Apple Device & Browser Compatibility Matrix — Master Spec

Reference blueprint for all phases of this feature. Each board ticket points here.

## Goal

QASE gets a first-class **Environment** entity: a systematically generated matrix of
Apple devices (iPhone / iPad / macOS), OS versions, browsers and browser versions —
each with a unique ID, BrowserStack-valid capabilities, filterable attributes and
version lifecycle (add/deprecate without touching test scenarios). A QA run
("test case") references ONE environment at execution time; the same scenario is
reusable across every environment. Execution history and reports preserve the exact
environment used (as a snapshot, so later edits/deprecations never rewrite history).

## Catalog contents

### Devices
- **iPhone**: 11, 11 Pro, 11 Pro Max, 12, 12 mini, 12 Pro, 12 Pro Max, 13, 13 mini,
  13 Pro, 13 Pro Max, 14, 14 Plus, 14 Pro, 14 Pro Max, 15, 15 Plus, 15 Pro, 15 Pro Max,
  16, 16 Plus, 16 Pro, 16 Pro Max, 16e, 17, 17 Air, 17 Pro, 17 Pro Max.
  Each entry: display name, `browserstackDeviceName`, screen size (inch), device type
  `mobile`, min iOS supported, supported OS versions.
- **iPad** (representative per model line): iPad, iPad mini, iPad Air, iPad Pro 11",
  iPad Pro 12.9", iPad Pro 13" — with generation/BrowserStack names, screen sizes,
  device type `tablet`.
- **macOS**: no device dimension on BrowserStack desktop; device label = OS default
  (e.g. "MacBook Pro"), device type `desktop`. OS versions: Monterey (12), Ventura (13),
  Sonoma (14), Sequoia (15), Tahoe (26). "Golden Gate" only if BrowserStack exposes it
  at build time.

### OS versions
Per device, include up to the **3 most recent OS versions it supports** AND that are
in the current support window (iOS 17 / 18.x / 26.x family; iPadOS same; macOS list
above). Concrete minor versions resolved at implementation time from BrowserStack's
published lists (https://www.browserstack.com/list-of-browsers-and-platforms/automate);
never invent versions.

### Browsers (validated against BrowserStack availability)
| Browser | iOS | iPadOS | macOS |
|---|---|---|---|
| Safari | ✅ | ✅ | ✅ |
| Chrome | ✅ | ✅ | ✅ |
| Firefox | ❌ (kept in catalog, marked unavailable) | ❌ | ✅ |
| Edge | ❌ | ❌ | ✅ |
| Opera | ❌ | ❌ | ✅ |
| Brave | ❌ | ❌ | ❌ |
| DuckDuckGo | ❌ | ❌ | ❌ |

Rules: only ✅ cells generate environments. Safari is **not** independently versioned —
its version is derived from the OS version (mapping table in the catalog, e.g.
iOS 18.3 → Safari 18.3; macOS Sonoma → Safari 17.x; Sequoia → 18.x; Tahoe → 26).
Chrome/Firefox/Edge/Opera use the latest ~4 major versions available on BrowserStack
for that platform, resolved at build time.

### Systematic generation
Expand the hierarchy `Platform → Device → OS Version → Browser → Browser Version`
with the rules above. Deduplicate by canonical ENV ID. Expected order of magnitude:
hundreds of environments, generated by code — never hand-entered.

## Environment record (canonical shape)

```json
{
  "envId": "ENV-IOS-IP16PRO-18.3-CHR-140",
  "platform": "ios",            // ios | ipados | macos
  "device": "iPhone 16 Pro",
  "os": "iOS",
  "osVersion": "18.3",
  "browser": "Chrome",
  "browserVersion": "140",
  "deviceType": "mobile",       // mobile | tablet | desktop
  "screenSize": "6.3 inch",
  "executionProvider": "browserstack",
  "isRealDevice": true,
  "active": true,
  "browserstackCapabilities": {
    "browserName": "chrome", "browserVersion": "140",
    "os": "ios", "osVersion": "18.3", "deviceName": "iPhone 16 Pro",
    "realMobile": true
  }
}
```

ENV ID scheme: `ENV-{PLAT}-{DEVICE_SLUG}-{OSVER}-{BROWSER3}-{BROWSER_MAJOR}` —
device slugs from a fixed map (IP16PRO, IP11PROMAX, IPADMINI, IPADAIR, IPADPRO11,
IPADPRO129, IPADPRO13, MAC-MONTEREY/VENTURA/SONOMA/SEQUOIA/TAHOE …). Uniqueness is
enforced by DB unique constraint and ID-generation function.

## Version management
- New browser/OS/device versions = catalog edit + regeneration seed; generator is
  idempotent (upsert by env_id; never deletes existing rows).
- Deprecation = `active=false`; inactive envs stay queryable and referenced by history,
  but not selectable for NEW runs.
- Runs store an **environment_snapshot** (full record copied at run start), so history
  and evidence never mutate.

## Filtering
`GET /api/environments` supports: `platform`, `device`, `os`, `osVersion`, `browser`,
`browserVersion`, `deviceType`, `executionProvider`, `active`, `isRealDevice`,
plus free-text `search` (matches envId/device/browser) and pagination. Same facets in
the admin UI.

## Execution integration
- Run creation (`POST /api/sessions|/api/sqa/sessions|/api/founder/sessions`) accepts
  `environmentId`; legacy `device` field still works (mapped to nearest env or kept as-is
  — backward compatible, never a breaking change).
- With BrowserStack credentials configured (`BROWSERSTACK_USERNAME` /
  `BROWSERSTACK_ACCESS_KEY`, stored as secret env keys): browser bridge connects via
  BrowserStack Playwright CDP endpoint using the env's capability map.
- Without credentials or with `executionProvider=local` envs: local Chromium emulation
  (viewport, UA, touch from the device data), clearly labeled **"emulated"** in UI and
  reports so nobody mistakes it for real Safari/WebKit.
- Reports, run list, execution history events and PDF include the environment identity
  (device, OS, browser, browser version, provider, real/emulated).
- Reproduce: "Re-run with same environment" uses the stored snapshot.

## Validation (user's 13-point checklist → automated tests + smoke checks)
Unique IDs; invalid combos rejected by API + generator; browser/OS versions stored
correctly; filters return exactly matching envs; run creation can select an env;
capability mapping well-formed; non-executable envs (Brave/DuckDuckGo, Firefox-on-iOS)
never generated and rejected if posted; adding a browser version doesn't duplicate or
alter existing runs; reports show exact env; failed runs reproducible from snapshot;
env data preserved in history/evidence.

## Phases
1. Catalog module (devices/OS/browsers/compatibility rules) + unit tests
2. DB schema, migration 015, systematic env generation (both stores)
3. Environments API + filtering + validation
4. Environments admin UI + picker integration
5. Run execution with environment (persistence, history, reports, reproduce)
6. BrowserStack integration (credentials, capability mapping, CDP execution, emulated fallback)
7. Validation suite & end-to-end smoke

Non-goals: Windows/Android expansion (deviceProfiles keeps existing entries), live
BrowserStack device-list sync (curated catalog, refreshed manually), classic
test-suite entities.
