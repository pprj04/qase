# D0.5 — Scoped UI Access Codes (team / demo access)

Status: **IMPLEMENTED** (2026-08-30) — 20/20 ui-access test cases pass; full regression battery green.
Audit: see D0.5 audit (conversation + `.drytis/notes/` handover context). This spec
implements the approved "smallest safe interim solution" only.

## Goal

Let teammates use the QASE UI **without ever receiving the master API token**.
Two roles, individually revocable access codes, server-side sessions in an
HttpOnly cookie. The master token remains the highest-privilege credential and
every existing authentication path keeps working unchanged.

## Non-goals (hard boundaries)

- No user accounts, no SSO, no full multi-user auth (that is a later build).
- B1 integration auth (`/api/v1/integration/*`, HMAC) — zero diff.
- C2/C3 autonomy, mission budget/governor, targetGuard/SSRF, Pulse/OpenAPI
  (`/api/v2`, `openapiDocument.js`), BrowserStack — zero diff.
- No plaintext access codes at rest, in logs, in URLs, or in any API response
  except the single mint response (shown once to the master-authed admin).
- No universal demo password; codes are per-teammate, role-scoped, revocable.

## Security model

- Codes: `22` random URL-safe chars, generated server-side. Stored as
  `scrypt1:<saltB64>:<hashB64>` (scrypt N=16384, r=8, p=1 — same params as
  secretStore's KDF) in `.qase/ui-access.json` with metadata only:
  `{ id, label, role, codeHash, createdAt, revokedAt?, lastUsedAt? }`.
- Sessions: 32-byte random id (base64url), kept **in memory only**; cookie
  `qase_session` (HttpOnly, SameSite=Strict, Path=/, Secure on https). Sliding
  TTL: 7 days default, `QASE_UI_SESSION_TTL_HOURS` override.
- Each request re-resolves the session → its code → revoked? expired? → so
  revoking a code invalidates its sessions immediately. Server restart clears
  in-memory sessions (users re-enter the code; acceptable for D0.5).
- Rate limit: 5 failed code attempts per source IP per 15 min → 429 with a
  generic message (no oracle about which part was wrong).
- Master token paths unchanged: Bearer header, `qase_token` cookie, `?token=`
  query (timing-safe compares). Session is an ADDITIVE 4th path.
- `request.auth = { kind: 'master' } | { kind: 'session', role, codeId, label }`
  is attached for handlers; absence means anonymous.

## Role matrix (enforced in ONE place: requireApiToken)

| Surface | Viewer | Operator | Master |
|---|---|---|---|
| `GET /api/*` reads | allow | allow | allow |
| `GET /api/config` | sanitized | sanitized | full |
| mission/test mutations (sessions create/message/stop/delete, `/api/v1/missions*` start/stop/iterate/revalidate, test-cases run, suites, workflows, schedules, findings edits, projects, knowledge, test-support) | 403 | allow | allow |
| config mutations (`PUT /api/config`, `/api/config/test`, `/api/config/test-browserstack`) | 403 | 403 | allow |
| admin/credential surfaces (`/api/auth/admin/*`, `/api/v1/webhooks`, `/api/v1/diagnostics/*/cleanup`) | 403 | 403 | allow |
| `/api/auth/session` POST/DELETE/GET | public-by-design | | |
| `/api/v1/integration/*` | B1 HMAC — untouched, separate middleware | | |
| `/api/v2/*` (Pulse) | session-authenticated reads allowed for viewer/operator (read-only surface) | | |

Method+path-prefix classification happens BEFORE handlers run; the only
non-GET allowances for sessions are `/api/auth/session` (logout) and — for
operator — the mission/test mutation list above.

`GET /api/config` sanitization for session roles removes:
provider, baseUrl, model, discoveryModel, executionModel, apiKey-related flags,
apiToken/apiTokenHint, and every browserstack* credential field (keeps
harmless UI prefs so boot works). Master token still sees everything.

## API surface (new)

- `POST /api/auth/session` `{ code }` → `204` + Set-Cookie `qase_session`;
  `401` invalid/expired/revoked (generic); `429` rate-limited.
- `DELETE /api/auth/session` → `204`, clears cookie.
- `GET /api/auth/session` → `{ authenticated: bool, kind, role? }` (whoami).
- `GET  /api/auth/admin/codes` (master) → metadata list, no hashes.
- `POST /api/auth/admin/codes` (master) `{ label, role }` → plaintext code
  shown ONCE in this response.
- `POST /api/auth/admin/codes/:id/revoke` (master) → metadata row.
- `POST /api/auth/admin/codes/:id/restore` (master) → re-enable.

## UI

- Gate (`#auth-gate`): two paths — "API token" input (unchanged behavior) and
  "Team access code" input → `POST /api/auth/session` → reload on success.
- Settings: new admin-only "Team access" section (label + role select + Create;
  list with label/role/created/active + Revoke/Restore). Plaintext code is
  shown exactly once in a copy-once box after mint; never again.
- Session users: Settings button hidden; run/mutation controls disabled via a
  `data-role` attribute on `<body>` set from whoami.

## Acceptance criteria (tests-real/ui-access.test.js)

1. Viewer code → session cookie set. 2. Viewer can GET permitted reads.
3. Viewer cannot POST missions (403). 4. Viewer cannot PUT config (403).
5. Operator code → session created. 6. Operator can POST a session/message
(mission mutation allowed). 7. Operator cannot PUT config / test-browserstack
(403). 8. Invalid code → 401. 9. Repeated invalid attempts → 429.
10. Revoked code → session rejected immediately + new login rejected.
11. Cookie has HttpOnly. 12. Cookie has SameSite=Strict. 13. `.qase/ui-access.json`
contains no plaintext code (hash only). 14. No API response echoes the code
(whoami/admin list/login errors). 15. Master Bearer token still works
(read + mutation + full config). 16. B1 HMAC integration auth still works
(signed whoami 200). 17. No code/token in server log output during the suite.
18. Role bypass attempts (method override, path casing, `/api/v2` writes,
unlisted mutation paths) → 403/401. 19. Restart (module re-import / new store
load) preserves codes; sessions cleared. 20. Expired session (TTL) rejected;
DELETE /api/auth/session logs out.
